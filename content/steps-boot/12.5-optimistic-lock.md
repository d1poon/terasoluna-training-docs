# Step 12.5 — 楽観ロック (Optimistic Lock) の実演

## このステップのゴール

これまでの Step 03-11 で作った変更画面は、実は**同時編集を想定していない**。
2 人の管理者が同じユーザ情報を同時に開いて片方が更新すると、もう片方の変更は**気づかず上書きされる (Lost Update)**。

このステップでは、`version` カラム + `WHERE version = #{version}` + 影響行数 0 → 業務例外の 3 点セットで
**「他人が先に更新していたら明示的にエラーを返す」**楽観ロックを実装する。

- 楽観ロック(Optimistic Lock)と悲観ロック(Pessimistic Lock)の違いが 1 文で言える
- `UPDATE ... WHERE id = ? AND version = ?` の意味 と 影響行数 0 のハンドリングを書ける
- `BusinessException` を投げて Controller で 409 相当の画面を出す流れを組める

> 💡 このステップはオプション (上級パターン)です。Step 12 で完成させたアプリはそのまま動きます。
> 「1 人しか触らない社内ツールでは不要、複数人が触る本番システムでは必須」という位置付けの、現場入門にほぼ必ず出るパターンです。

## 事前準備

- [Step 11](/steps-boot/11-edit) 完了 (変更画面が動く、PRG パターンが理解できている)
- Step 12 の自己確認 12 問が通っていると理想的

## 楽観ロックとは (1 文)

**楽観ロック**: 「みんな同時に更新しないよね」と楽観して、更新時に「自分が読んだ時から誰かが更新してない?」を SQL の WHERE 条件でチェックする方式。誰も触ってなければ更新される、誰かが先に更新していたら 影響行数 0 で失敗する。

**悲観ロック**: 逆に「みんな同時に更新するかも」と悲観して、SELECT 時点で `SELECT ... FOR UPDATE` で行をロックし、他プロセスを待たせる方式。

このステップは楽観ロックを扱う。悲観ロックは同時更新が本当に多い場合や、ロック期間が短い場合に使う。

```sql
DROP TABLE IF EXISTS users;

CREATE TABLE users (
    id       VARCHAR(50)  PRIMARY KEY,
    password VARCHAR(255) NOT NULL,
    role     VARCHAR(50)  NOT NULL,
    version  INT          NOT NULL DEFAULT 0   -- ← 追加: 楽観ロック用
);
```

#### なぜこう書く

- **① `version INT NOT NULL DEFAULT 0`** — 各行に「何回更新されたか」のカウンタを持たせる。挿入時 0、更新するたびに +1 する
- **② `NOT NULL`** — NULL 混入で `WHERE version = ?` が常に false になる罠を防ぐ (Oracle だと NULL = NULL は false)

`updateRole` の SQL を楽観ロック対応に置き換える。`SELECT` は version も返す。

```xml
<!-- 既存の findById を修正: version を返す -->
<select id="findById" resultType="com.example.rolemgr.domain.User">
    SELECT id, password, role, version
    FROM users
    WHERE id = #{id}
</select>

<!-- 既存の updateRole を書き換え: WHERE に version 条件を追加 -->
<update id="updateRole">
    UPDATE users
    SET role    = #{role},
        version = version + 1
    WHERE id      = #{id}
      AND version = #{version}
</update>
```

#### なぜこう書く

- **① `SET version = version + 1`** — 更新が成功したら version を 1 増やす。次回の更新でこの新しい version を持っていない人は失敗する
- **② `WHERE id = #{id} AND version = #{version}`** — 「自分が読んだ時の version」と DB の現在 version が一致する時だけ更新する
- **③ 影響行数** — MyBatis の `<update>` は影響行数 (`int`) を返す。version 不一致だと該当行なしで `0` が返る。ここで判定する

```java
package com.example.rolemgr.service;

import com.example.rolemgr.domain.User;
import com.example.rolemgr.repository.UserMapper;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional
public class UserService {

    private final UserMapper userMapper;

    public UserService(UserMapper userMapper) {
        this.userMapper = userMapper;
    }

    public User findById(String id) {
        return userMapper.findById(id);
    }

    /**
     * 役職を更新する。version が一致しない場合 (= 他人が先に更新した場合) は
     * BusinessException を投げる。
     */
    public void updateRole(String id, String role, int version) {
        int affected = userMapper.updateRole(id, role, version);
        if (affected == 0) {
            // version 不一致 or 行が消えている → 楽観ロック失敗
            throw new BusinessException("他のユーザが先に更新しました。もう一度読み込んでから編集してください。");
        }
    }
}
```

新しい例外クラスを追加:

```java
// service/BusinessException.java
package com.example.rolemgr.service;

/** 業務例外 (システム例外と区別するためのマーカー) */
public class BusinessException extends RuntimeException {
    public BusinessException(String message) {
        super(message);
    }
}
```

#### なぜこう書く

- **① 影響行数 0 = 楽観ロック失敗** — SQL 実行自体は成功 (エラーではない) だが、更新した行が 0 件。これは version 不一致 or 該当行が削除済みのどちらか
- **② `RuntimeException` を継承した業務例外** — トランザクションを rollback させたいので `RuntimeException` 系にする (Spring はデフォルトで検査例外を rollback しない)
- **③ `BusinessException` という名前** — 「業務ルール上の失敗」と「システム障害 (DB 落ちた等)」を分離するための命名。前者はユーザにわかる形で表示、後者はエラーページに遷移

Step 11 で定義した `edit()` メソッドを、次の `update()` に置き換える。編集画面のフォームで hidden として version を返して、更新時に受け取る。

```java
@PostMapping("/user-info/edit")
public String update(
        Principal principal,              // ← Step 10/11 と同じく、ID はここから取る
        @RequestParam String role,
        @RequestParam int version,        // ← hidden から受け取る
        RedirectAttributes redirect) {
    try {
        userService.updateRole(principal.getName(), role, version);
        redirect.addFlashAttribute("message", "更新しました");
        return "redirect:/user-info";  // PRG
    } catch (BusinessException e) {
        redirect.addFlashAttribute("error", e.getMessage());
        return "redirect:/user-info/edit";  // 編集画面に戻す (最新版が読み直される)
    }
}
```

そして `userInfoEdit.jsp` は version の hidden だけ追加する (id の hidden は追加しない):

```jsp
<form action="/user-info/edit" method="post">

    <input type="hidden" name="${_csrf.parameterName}" value="${_csrf.token}" />
    <input type="text" name="role" value="${user.role}" />
    <button type="submit">更新</button>
</form>

<c:if test="${not empty error}">
    <div class="error">${error}</div>
```

#### なぜこう書く

- **ID は `Principal` から取る、`@RequestParam` では受け取らない** — Step 10 で教えた IDOR 対策 (「URL / フォーム値でユーザ ID を渡さない、サーバ側で認証情報から確定する」) は変更処理でも同じく必須。もし `id` を hidden やクエリパラメータで受け取ると、開発者ツールで値を書き換えて**他人の役職を更新できてしまう**。`version` は「楽観ロックの判定用の値」であって「更新対象を特定する ID」ではないので hidden で送っても問題ないが、ID は必ずサーバ側で確定する

## よくある詰まり

- **常に 0 行 → 全部失敗する**: JSP の hidden で version を返し忘れ、Controller が受け取れず 0 として送っている。ブラウザの開発者ツール で送信内容を確認
- **version が増えない**: `SET version = version + 1` を忘れている、または UPDATE 文が別の SQL に上書きされている
- **`BusinessException` が rollback されない**: `@Transactional` の `rollbackFor` に業務例外を追加する (`@Transactional(rollbackFor = Exception.class)` にすると全例外で rollback する)
- **Oracle だと動くけど H2 だと動かない (逆も)**: NULL 混入。`version` 列に NULL が入っていると `WHERE version = 0` が常に false。DEFAULT 0 と NOT NULL を必ず付ける

## 悲観ロック (Pessimistic Lock) との使い分け

| 状況 | 楽観ロック | 悲観ロック |
|---|---|---|
| 同時更新の頻度 | 低い (競合まれ) ⭕ | 高い (常に競合) ⭕ |
| ロックの粒度 | 行単位、瞬間 | 行単位、SELECT 〜 COMMIT の間ずっと |
| 待機 | しない (すぐエラー) | する (他が終わるまでブロック) |
| ユーザ体験 | 「もう一度」を求める | 待たされる |
| 実装 | version 列 + WHERE 条件 | `SELECT ... FOR UPDATE` |
| 現場での頻度 | Web の CRUD 画面で主流 ⭐ | 在庫引き当て、決済など |

Web アプリの多くの画面 (プロフィール編集、設定変更) では楽観ロック で十分。
「在庫を 1 つ引く」「口座から差し引く」等、絶対に取り逃したくないシチュエーションで悲観ロックを使う。

## 発展: 楽観ロックの応用パターン

- **JPA/Hibernate**: `@Version` アノテーションを付けたフィールドを自動でこの仕組みで扱う
- **TERASOLUNA**: `common-library` の `PessimisticLockException` / `OptimisticLockException` が用意されている。業務例外の型分けの参考に
- **フロントエンドとの分離**: SPA なら 409 Conflict の HTTP ステータスで返す設計にする ("最新を GET しなおしてリトライ")
