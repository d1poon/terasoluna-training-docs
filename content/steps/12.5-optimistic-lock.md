# Step 12.5 — 楽観ロック (Optimistic Lock) の実演

## このステップのゴール

Step 11 の変更画面は「同時編集」を想定していない。2 人の管理者が同時に開いて片方が更新すると、もう片方の変更が**気づかず上書きされる (Lost Update)**。

このステップでは、**`version` カラム + `WHERE version = #{version}` + 影響行数 0 → `BusinessException`** の 3 点セットで、
「他人が先に更新していたら明示的にエラーを返す」楽観ロックを実装する。

- 楽観ロックと悲観ロックの違いが 1 文で言える
- `UPDATE ... WHERE id = ? AND version = ?` の意味と影響行数 0 のハンドリングを書ける
- `BusinessException` を投げて Controller で 409 相当の画面を出す流れを組める

> このステップはオプション (上級パターン)。Step 12 で完成させたアプリはそのまま動きます。

## 楽観ロックとは (1 文)

**楽観ロック**: 「みんな同時に更新しないよね」と楽観して、更新時に「自分が読んだ時から誰かが更新してない?」を SQL の WHERE 条件でチェックする方式。

**悲観ロック**: 「みんな同時に更新するかも」と悲観して、SELECT 時点で `SELECT ... FOR UPDATE` で行をロックし、他プロセスを待たせる方式。

Web アプリの CRUD 画面では楽観ロックが主流。「在庫引き当て」「決済」等、絶対に取り逃したくない処理では悲観ロック。

### 2. `User.java` に version フィールド追加

```java
public class User implements Serializable {
    private String id;
    private String password;
    private String role;
    private int version;                                        // 追加

    public int getVersion() { return version; }
    public void setVersion(int version) { this.version = version; }
    // 他 getter/setter は既存
}
```

### 3. `UserRepository.xml` の SELECT + UPDATE を書き換え

```xml
<select id="findById" resultType="com.example.demo.domain.model.User">
    SELECT id, password, role, version FROM users WHERE id = #{id}
</select>

<update id="updateRoleWithLock">
    UPDATE users
       SET role    = #{role},
           version = version + 1                                <!-- ① -->
     WHERE id      = #{id}
       AND version = #{version}                                 <!-- ② -->
</update>
```

- **① `SET version = version + 1`** — 更新成功時に version カウンタを 1 増やす
- **② `WHERE id = #{id} AND version = #{version}`** — 「自分が読んだ時の version」と DB 現在値が一致する時だけ更新

### 4. `UserRepository.java` にメソッド追加

```java
int updateRoleWithLock(@Param("id") String id,
                       @Param("role") String role,
                       @Param("version") int version);
```

### 5. `UserServiceImpl.java` で影響行数を判定

```java
@Override
public void updateRoleWithLock(String id, String role, int version) {
    int affected = userRepository.updateRoleWithLock(id, role, version);
    if (affected == 0) {
        throw new BusinessException(
            "他のユーザが先に更新しました。もう一度読み込んでから編集してください。");
    }
}
```

新しい例外クラス:

```java
// domain/service/user/BusinessException.java
package com.example.demo.domain.service.user;

public class BusinessException extends RuntimeException {                      // ①
    public BusinessException(String message) {
        super(message);
    }
}
```

- **① `RuntimeException` 継承** — `@Transactional` がデフォルトで rollback する対象になる (checked exception だと rollback されない、TERASOLUNA 規約でもこちらに寄せる)

### 6. `UserInfoController.java` で受け止め

```java
@PostMapping("/user-info/edit")
public String update(
        Authentication auth,
        @Valid @ModelAttribute UserInfoUpdateForm form,
        BindingResult bindingResult,
        RedirectAttributes redirect) {
    if (bindingResult.hasErrors()) return "userinfo/userInfoEdit";
    try {
        userService.updateRoleWithLock(
            auth.getName(), form.getRole(), form.getVersion());
    } catch (BusinessException e) {
        redirect.addFlashAttribute("error", e.getMessage());
        return "redirect:/user-info/edit";
    }
    redirect.addFlashAttribute("message", "役職を更新しました");
    return "redirect:/user-info";
}
```

`UserInfoUpdateForm` に `int version` フィールドを追加、`userInfoEdit.jsp` に version 用の hidden を追加:

```jsp
<form:hidden path="version" />
```

## よくある詰まり

- **常に 0 行 → 全部失敗**: JSP の hidden で version を返し忘れ、Controller が受け取れず 0 として送っている
- **version が増えない**: `SET version = version + 1` を書き忘れ、または別の SQL に上書きされている
- **`BusinessException` が rollback されない**: `@Transactional(rollbackFor = Exception.class)` にする、または `RuntimeException` 継承であることを確認
- **NULL 混入で `WHERE version = 0` が常に false**: DDL の `NOT NULL DEFAULT 0` を書き忘れ (Oracle だと NULL = NULL は false)

## 発展

- **JPA/Hibernate**: `@Version` アノテーションで自動化
- **TERASOLUNA common-library**: `OptimisticLockException` / `PessimisticLockException` を業務例外の型分けの参考に
- **SPA との連携**: 409 Conflict の HTTP ステータスで返し、フロントが「最新を GET しなおしてリトライ」の設計
